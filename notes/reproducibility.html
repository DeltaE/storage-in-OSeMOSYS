Reproducibility guide#

This page explains how to regenerate the results of

Borba, B., Islam, M. E., & Niet, T. Storage in Long-Term Energy Planning Models with Temporal Aggregation: Best Practices and Algorithms. Environmental Research Communications (2026).

from this repository, which result comes from which step, how long each step takes, and what was verified. The executable version of this guide is the notebook Reproducing the study step by step (notebooks/reproduce_study.ipynb in the repository).

3. Step by step#

3.1 Install#

git clone https://github.com/DeltaE/storage-in-OSeMOSYS.git
cd storage-in-OSeMOSYS
conda env create -f env/environment-crossplatform.yml
conda activate storage_osemosys

3.2 Quick verification (about 2 minutes)#

jupyter lab notebooks/reproduce_study.ipynb   # run all cells with the default switches

With the default switches the notebook:

  1. checks the installed versions against the paper;

  2. lists the model inputs and plots the time series;

  3. reruns the clustering, checks that it is deterministic, and repeats it with seeds 1–9;

  4. runs the hand-calculated SoC verification;

  5. solves k4h1 for the three systems with all four formulations (12 LPs) and compares cost, VRE capacity and storage capacity with the archived results (the cell fails if they differ);

  6. rebuilds Table 4, the cost-error curves, the stress-test statistics and the SoC metrics from the archived results.

Conventions used throughout:

  • Errors are relative to the k365h1 Novo run of the same system, computed from unrounded values.

  • Storage capacity in the tables is new capacity; total capacity adds the 0.05 kW·yr residual.

  • Stress-test violations count hours with SoC strictly above the cap or below zero. Hours exactly at the cap are feasible and are reported separately.

  • Figure 8 metrics: each aggregated trajectory is expanded to 8760 hours. Novo and Kotzur use chronological blocks (Kotzur reconstructed within days); Welsch uses its reconstructed trajectory in grouped day-type order; Niet holds each representative block for its year-split duration. Rainflow counting follows ASTM E1049-85, with half cycles counted as 0.5.

6. Numerical and platform notes#

  • Determinism. With the same GLPK version and inputs, solutions are identical across runs. Different GLPK builds or platforms can follow different simplex paths. The optimal objective is unchanged, but degenerate LPs can return different, equally optimal, capacities or SoC trajectories.

  • Solver failures. GLPK’s primal simplex occasionally stops on a Welsch LP with “unable to recover undefined or non-optimal solution”, depending on the platform. The pipeline detects this and re-solves with --nopresol, --dual and --exact; in the cases tested all three give the same optimum. Eight Welsch rows of the original sweep (k4h12, k6h2, k6h8 HYD; k5h1, k7h1, k8h1 SOL; k5h4, k7h8 WND) were affected. The re-solved values are in data/published_results/corrections/welsch_reruns.xlsx, and the notebook uses them.

  • Clustering. n_init = 1 and random_state = 0 are set explicitly. Partitions differ between seeds, so error levels at a given k depend on the clustering. The notebook quantifies this (step 11).

  • Runtimes and memory depend on hardware and solver. Ratios between formulations are more transferable than absolute values, and memory ratios more than time ratios.

7. Changes made for the published version#

The code was corrected after the original runs so that a fresh clone reproduces the archived results. None of the corrections changes the model equations.

Change

Reason

Template CSVs are copied before the formulation-specific files are generated

The previous order overwrote the Kotzur and Welsch mapping files with empty templates

data/system/ (formerly inputs_csv/) holds the values used in the paper (demand 20, VRE capital cost 1200, VRE variable cost 20)

The repository previously contained placeholder values

Model result folders are created at run time; stale results are cleared

Fresh clones failed; failed solves could report results of the previous run

Solver status check and automatic retry

See section 6

Explicit n_init, random_state and clustering record per run

Clustering is reproducible across scikit-learn versions and traceable

Sparse chronological mapping for the Kotzur reconstruction

Kotzur post-processing no longer requires the 12 GB Novo run

Cross-platform environment, headless plotting, UTF-8 child processes

Runs on Windows, macOS and Linux

Documentation changes#

The tutorial pages Basic usage, Comparative analysis and Advanced configuration, and the Results analysis page, described functions and features that the code does not provide. They are no longer published (copies are in archive/docs/). The module overview, configuration, workflow, environment and model-specification pages were rewritten to match the code, and the full API reference is generated from the source (src).
